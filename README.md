# Прогноз выполнения плана взысканий

Прогноз всего следующего месяца фиксируется **до его начала**. Утверждённый план по будущим датам используется напрямую. Факт целевого месяца служит только для последующей оценки.

Основная ошибка на дату: `100 × abs(прогноз_накопленный − факт_накопленный) / план_накопленный`, в **процентных пунктах**. Общая эффективность считается как отношение сумм, а не среднее процентов сегментов. Строгая цель — не больше 1 п.п. на каждой дате с положительным планом. Средняя ошибка, ошибка конца месяца и доля попаданий выводятся отдельно. Прогноз не ограничивается 100% выполнения.

**Достижение 1 п.п. на рабочей базе пока не проверено.** Автоматические проверки и `--demo` используют искусственные данные и проверяют корректность расчётов, а не бизнес-точность.

## Python: один DataFrame

**Для исходного RR-запроса** `SUM(w1-w2-cession-write_off) AS fact, SUM(target) AS plan` выбирайте `fact_mode="cumulative"` и `plan_mode="cumulative"`: это снимки на дату. `daily` для такого входа накапливает суммы повторно. В исправленном ноутбуке эти параметры уже заданы.

**Для старого работающего `upload_model_effect.py` используйте `forecast_YYYY-MM.csv`** из каталога результатов (ноутбук также сохраняет его рядом с собой). Загрузчик менять не нужно. Файл содержит ровно одну строку на дату, накопленные `fact/plan`, `dt_in` и `forecast_date` равны первому числу месяца, как в старом загрузчике. Это отдельное соглашение дашборда для метки расчёта; реальный cutoff обучения сохраняется в `origin`/`manifest.json`. Подготовленный DataFrame доступен как `result["dashboard_upload"]`. Для этого пути не нужен новый адаптер. Сохраните старые вызовы загрузки и обновления витрины; код самого `DataBaseConnector` и дашборда отсутствует в этом репозитории.

Для вашей основной задачи — **общего выполнения плана по портфелю** — используйте `forecast_grain="total"`. Он суммирует снимки по дате до создания календарной сетки и до преобразования накопленных сумм в дневные. Изменение состава DPD/PVR/когорт между датами не требует искусственного плана для каждой исчезнувшей комбинации. Вход при этом должен содержать **полный снимок портфеля на каждой дате**, а его суммы должны совпадать с общим отчётом. Этот режим не восстанавливает отсутствующие исходные строки.

```python
from collections_forecast import Config, run

config = Config(
    forecast_month="2026-11",
    forecast_grain="total",
    fact_mode="cumulative",     # RR-снимок сбора на дату
    plan_mode="cumulative",     # RR-снимок target на дату
    output_dir="outputs/2026-11-total",
)

# df: date, fact, plan за исторические месяцы и целевой месяц.
# Будущий план и факт могут отсутствовать (NaN).
result = run(df, config=config)
forecast = result["forecast"]
comparison = result["comparison"]  # None, если целевого факта ещё нет
upload = result["upload"]  # готовые строки существующей таблицы forecast
daily_totals = result["daily_totals"]  # общий дневной прогноз для сверки
print(result["plan_status"])  # почему выбран основной или резервный режим
```

Можно передать настройки непосредственно: `run(df, forecast_month="2026-11", fact_mode="daily", plan_mode="daily")`.

Для уже созданного конфига:

```python
from dataclasses import replace
config = replace(config, forecast_grain="total", output_dir="outputs/forecast_total_v2")
result = run(df, config=config)
print(result["plan_status"])
```

Используйте новый `output_dir`, поскольку прежний прогноз зафиксирован и не перезаписывается другим результатом. При `total` факт, план, обучение и проверка используют одну общую детализацию; итог содержит одну строку на дату. Полная история позволяет выполнить подбор и контроль моделей вместо резервного прогноза из-за искусственных сегментных пропусков. Настройки `fact_mode/plan_mode` по-прежнему должны соответствовать источнику, автоматически они не меняются.

В библиотеке значение по умолчанию остаётся `forecast_grain="segments"` для совместимости; в готовом ноутбуке выбран `total`. Сегментный режим нужен для прогноза с фильтрами по сегментам и требует полных устойчивых рядов. В режиме `total` дополнительные сегментные файлы `portfolio_path/inflow_path/operations_path/reference_path` пока не поддерживаются: используются портфельные поля исходного DataFrame и календарь. `calendar_path` поддерживается. Отбор версий факта и плана по датам доступности выполняется до агрегации.

Реально отсутствующий день плана или явно пустой план в исходной строке остаётся неизвестным и сохраняет резервный режим. В частности, NULL не отбрасывается при суммировании плана других сегментов.

Также `run(df)` принимает исходные имена `report_dt`, `target` и компоненты `w1,w2,cession,write_off`: они преобразуются в `date,plan,fact`. Если есть `is_forecast`, в историю и факты сравнения попадают только строки 0. Исторические планы берутся из строк 0, план целевого месяца — из `plan_is_forecast`. Разные виды строк не складываются. Для обычного входа без флага считается, что источники уже разделены пользователем.

## Итоговый CSV для БД без размножения сумм

После успешного `run(df, config=config)` файл **`<output_dir>/forecast_upload.csv`** содержит строки для существующей таблицы **`forecast`** из описания БД. Одна строка на дату и сегмент модели. Для общего входа `date,fact,plan` получается 28–31 строка, для N сегментов — N × число дней. Каждая строка содержит сумму своего сегмента, общий итог в сегментах не повторяется.

| Поле | Смысл |
|---|---|
| `report_month` | Первое число целевого месяца |
| `report_dt` | Дата прогнозного снимка |
| `dt_in` | Пустая строка: когорты уже агрегированы, нельзя размножать прогноз по исходным датам входа |
| `subproduct, dpd_bucket, pvr_bucket, terbank, inflow` | Сегмент, которому принадлежит сумма |
| `fact` | **Прогноз** накопленного сбора на `report_dt`, в денежных единицах входа |
| `plan` | Накопленный план на ту же дату; неизвестный план = SQL NULL |
| `dolg` | Замороженный доступный долг сегмента; в резервном режиме NULL |
| `is_forecast` | 1 |
| `forecast_date` | Дата выпуска: последний день предыдущего месяца |
| `forecast_model` | `collections.v2` |

Для агрегатных измерений используются соглашения вашей витрины: пустые `subproduct/dpd_bucket`, `terbank='МБ'`, `pvr_bucket='0. [undef]'`. Передавайте `inflow`, если нужно отдельно сохранить новые входы; вход без этого признака получает 0, как в адаптере общего ряда. Даты в CSV записаны ISO `YYYY-MM-DD`; если ваш загрузчик хранит числовые даты, преобразуйте их в используемый БД формат на этапе импорта. Пустые денежные ячейки — NULL, пустой `dt_in` — признак агрегации.

**Месячный прогноз** = сумма `fact` по сегментам **только на последнюю дату месяца**. Нельзя суммировать накопленные снимки за все даты. Для сверки сохраняется `forecast_daily_totals.csv`: ровно одна строка на дату, `forecast_daily` и `plan_daily` за день. Сумма его `forecast_daily` равна итогу `fact` последней даты загрузочного файла. Этот проверочный файл не загружается вторым прогнозом той же модели. Точный выбранный метод остаётся в `manifest.json` и аналитическом `forecast.csv`.

Повторная загрузка должна **заменять весь срез `(report_month, forecast_model, forecast_date)` в одной транзакции**, согласно описанию `upload_forecast`, а не добавлять копии через append. Это также убирает прежние строки исчезнувших сегментов. Уникальный ключ строки: этот срез + `report_dt,dt_in,subproduct,dpd_bucket,pvr_bucket,terbank,inflow`. `forecast_upload_schema.json` содержит ключ, число строк и контрольную сумму прогноза за месяц. Перед сохранением проверяются уникальность и покрытие месяца; совпадение разных сегментов после приведения обозначений к формату БД останавливает выгрузку.

Не присоединяйте прогноз к сырым строкам `rr1plus_data_raw` только по дате/сегменту: 100 исходных когорт повторят прогноз сегмента 100 раз. Сначала агрегируйте факт до той же детализации «дата × сегмент». В pandas используйте `validate="one_to_one"`. Не восстанавливайте `dt_in` через JOIN к исходной таблице. Для общего сравнения сначала агрегируйте обе стороны до одной строки на дату.

### Почему ranking и control пустые

Это штатный **резервный денежный прогноз**, который включается при неизвестном плане, отсутствии плана для части исторических сегментов либо нулевом плане. Подбор и контроль моделей в этом режиме не выполняются; точность 1 п.п. не считается проверенной. `result["plan_status"]` и `forecast_run_status.json` показывают причину, неизвестные даты и примеры отсутствующих сегментов. Чтобы использовать основной режим, передайте полный известный план целевого месяца для тех же сегментов. Если плановые строки в исходном `df` помечены 1, задайте `plan_is_forecast=1`; не меняйте этот флаг без проверки источника. Пропуски плана заполнять нулями только ради запуска модели нельзя.

### Загрузчик агрегатной линии дашборда

Для загрузчика, который ставит пустые продукт/DPD, `МБ`, `0. [undef]`, `inflow=0` и берёт **общий** долг на дату, предназначен **`forecast_upload_total.csv`** (`result["upload_total"]`). В нём ровно 28–31 строка и та же схема таблицы `forecast`. Здесь `fact/plan` уже накопленные: повторно вызывать `cumsum` нельзя. Это общий портфель; фильтрация отдельных продуктов/DPD/inflow для такой линии не поддерживается. Для сегментных фильтров используйте исходный `forecast_upload.csv`, сохраняя его измерения и сегментный долг.

Не присваивайте общий долг каждой строке сегментного CSV и затем не стирайте сегменты: на дате с N сегментами получится N копий общего долга. Отношение прогнозного сбора к долгу уменьшится в N раз. KPI `fact/plan` от одинаковой подмены долга сам по себе не меняется: скачки этого KPI нужно проверять по денежным числителю и знаменателю.

Положите [`dashboard_upload_adapter.py`](dashboard_upload_adapter.py) рядом с вашим `upload_model_effect.py`. Это самостоятельный файл, установка пакета проекта не нужна. После чтения CSV и запроса `dolg_df` замените блоки `days.map(...)`, `dolg.ffill().fillna(0)` и ручного `pd.DataFrame(...)` следующим кодом:

```python
from dashboard_upload_adapter import aggregate_database_upload

# fc = pd.read_csv(CSV, encoding="utf-8-sig")
# CSV — forecast_upload.csv или forecast_upload_total.csv из нового ноутбука.
# dolg_df — ваш запрос с колонками report_day, dolg, одна строка на день.
df = aggregate_database_upload(
    fc,
    report_month=REPORT_MONTH,
    debt_by_day=dolg_df,
    forecast_model=MODEL,
)
print("Строк для загрузки:", len(df))
print("Прогноз на конец месяца:", df.iloc[-1][["report_dt", "fact", "plan", "dolg"]])
print("Дата расчёта из CSV:", df.forecast_date.iloc[0])
db.upload_forecast(df)  # существующая замена среза, не append
```

Адаптер сначала суммирует прогноз и план по сегментам **на каждую дату**, затем присоединяет общий долг ровно один раз. Перенос последнего известного долга идёт по отсортированным календарным датам, не по порядку строк разных сегментов. Неизвестный долг до первой доступной даты остаётся NULL. План не заменяется, не заполняется нулём и не берётся из будущего факта. Даты месяца и дата выпуска из CSV проверяются и сохраняются: октябрьский файл нельзя переименовать в ноябрьский. Выберите в дашборде дату расчёта из загруженного CSV; старый срез с другим `forecast_date` не изменяется.

`debt_by_day` из факта целевого месяца — только знаменатель для визуального сравнения RR. Он не используется в модели или историческом прогнозе «до начала месяца». Без этого аргумента берётся сумма исходного прогнозного долга, а не будущий факт. Загружайте **один** вариант — сегментный либо агрегатный; одинаковые модель/месяц/дата выпуска должны заменять один срез.

Для диагностики скачка после 25-го дня непосредственно перед загрузкой:

```python
check = df[["report_dt", "fact", "plan", "dolg"]].copy()
check["kpi_pct"] = 100 * check.fact / check.plan.where(check.plan.gt(0))
check["fact_rr_pct"] = 100 * check.fact / check.dolg.where(check.dolg.gt(0))
check["plan_rr_pct"] = 100 * check.plan / check.dolg.where(check.dolg.gt(0))
display(check.loc[check.report_dt.dt.day.between(24, 27)])
```

Если скачок уже есть в `check`, он приходит из исходных сумм прогноза/плана. Если его нет, сравните эти же суммы с SQL-агрегацией витрины для **той же** модели, даты расчёта, месяца и фильтров. Фотография графика не позволяет установить, меняется ли числитель, знаменатель или состав выбранных строк.

## Если входные данные не принимаются

При `run(..., save=True)` полная причина сохраняется в `<output_dir>/input_error.txt`. Ошибки чисел показывают колонку, число проблемных строк и примеры; ошибки дублей — ключ и примеры; если отклонены все обучающие месяцы, перечисляются причины по месяцам.

Снимки `w1 - w2 - cession - write_off` и `target` на дату могут быть накопленными. Если в вашем отчёте это накопленные суммы, задайте `fact_mode="cumulative"`, `plan_mode="cumulative"`. Объявление накопленного ряда дневным повторно накапливает одни и те же деньги. Режим нельзя надёжно определить только по росту значений — сверьте его с исходным отчётом.

Если DPD/PVR-бакет меняется между снимками, ряд внутри такого сегмента не является стабильной накопленной когортой. Для общего прогноза можно передать сверенный общий `date,fact,plan` по дням, где состав портфеля и смысл накопления согласованы с отчётом. Для детализации нужны устойчивые когорты или сверенные дневные платежи. Пропуски снимков и повторные строки автоматически нулями не заменяются и не складываются.

Необязательные сегменты: `subproduct, dpd_bucket, pvr_bucket, terbank, inflow`; отсутствующие сегменты объединяются в группу «ВСЕ». Если есть `dt_in`, он сохраняется до агрегации когорт. Повторяющиеся строки одного ключа запрещены; несколько платежных транзакций сначала нужно агрегировать до согласованной дневной детализации. Факт будущих дат не используется в признаках или обучении. Если он присутствует, сравнение выполняется после построения и сохранения прогноза.

## Python: отдельные история, планы и факты

```python
from collections_forecast import Config, ForecastRunner

config = Config(
    forecast_month="2026-11", fact_mode="cumulative", plan_mode="cumulative",
    plan_available_column="plan_known_at",  # если есть архив дат доступности
    raw_available_column="available_at",    # если есть версии фактов
    output_dir="outputs/2026-11",
)
runner = ForecastRunner(config, history_df=df_history, plan_df=df_plan)
runner.audit()
ranking, selection = runner.select()
control = runner.control()
forecast = runner.forecast()

# Позднее, когда получен факт целевого месяца:
segments, total, metrics = runner.compare(actual_df=df_actual)
```

`df_history` содержит только даты до целевого месяца. `df_plan` содержит планы исторических и целевого месяцев. `df_actual` относится только к целевому месяцу. Также доступен вызов `run(df_history, df_plan, df_actual, config=config)`.

Ключ исходной строки RR: `report_month, report_dt, dt_in, subproduct, dpd_bucket, pvr_bucket, terbank, inflow`. Вместо `report_dt` можно передать `date`.

История содержит готовый `fact` либо компоненты `w1, w2, cession, write_off`, из которых вычисляется `w1 − w2 − cession − write_off`; для исторических строк требуется `target`. При использовании компонентов RR требуются также `acc_count, avg_dpd, avg_pvr` (средние могут быть NaN). Для готового факта портфельные поля необязательны. План содержит `target` либо колонку, заданную через `plan_value_column`. `report_month` — первое число месяца; `dt_in` — дата входа когорты.

В истории допускаются только `is_forecast=0`. В переданном плане выбирается значение `plan_is_forecast` (по умолчанию 0); фактические и прогнозные строки не суммируются вместе. Исторические планы для обучения должны быть полными. Пропуски будущего плана не останавливают денежный прогноз. Строки до появления первой плановой новой когорты могут дополняться структурным нулём плана. Отсутствующий факт автоматически нулём не становится.

### Если будущего плана нет

Прогноз строится до последнего дня месяца даже при пропущенной дате, отсутствии целого сегмента или всех будущих строк. Автоматически включается резервный денежный прогноз `fallback_history_curve`: средняя накопленная кривая сборов последних полных исторических месяцев переносится на длину целевого месяца. При неполной истории используются средние сборы по дням недели. Для совершенно нового сегмента применяется явно обозначенный `cold_start_plan_or_zero`: доступный план как предварительная оценка, а при отсутствии любых сумм — ноль. Это резервная оценка, её точность требует отдельной проверки.

Неизвестный официальный план сохраняется как `NaN` и отмечается `plan_missing`. После разрыва дневного плана накопленный знаменатель и проценты выполнения недоступны. Ошибка в п.п. и достижение цели 1 п.п. не объявляются подтверждёнными. При накопленном плане пропуск снимка делает неизвестными оба соседних дневных приращения; скачок не приписывается одному дню. Прогнозный режим отмечается в `audit.json` и `model_status.csv`.

В резервном режиме `run()` не требует подбора моделей и возвращает пустые `ranking` и `control`, `selection=None`. Резервный прогноз использует только исторические платежи; будущий факт не влияет на него. Ограничения на неверные даты, дубли и нечисловые значения остаются в силе.

## Дневные и накопленные значения

`fact_mode` и `plan_mode` обязательны:

- `daily`: сумма за день; накопление выполняется один раз внутри месяца.
- `cumulative`: сумма с начала отчётного месяца либо входа когорты внутри него. После выбора доступной версии снимка рассчитываются дневные приращения по стабильному ключу когорты и сегмента.

Накопленный показатель за всё время жизни договора без сброса в начале отчётного месяца нужно предварительно привести к этой схеме. Нельзя считать первое значение в середине месяца дневным сбором. В режиме `cumulative` пропущенные снимки, изменение состава ключей и исчезновение когорт требуют сверки: функция откажется соединять разрыв или угадывать нули. Отрицательные приращения факта сохраняются как корректировки; отрицательные дневные планы отвергаются.

Для сверки с независимым отчётом передайте `report_checks_path` в `run()` либо вызовите `runner.verify_report(path)`. Формат CSV: `date,fact_daily,plan_daily`. Проверяются даты до прогнозируемого месяца с точностью до 0,01 денежной единицы.

## Командная строка и SQLite

```bash
python collections_forecast.py --input daily.csv --month 2026-11 --fact-mode daily --plan-mode daily --output outputs/2026-11
python -m collections_forecast --db input/m1p_database_v2.db --month 2026-11 --fact-mode cumulative --plan-mode cumulative --output outputs/2026-11
python -m collections_forecast --history history.csv --plan plans.csv --month 2026-11 --fact-mode daily --plan-mode daily
```

`--actual actual.csv` включает отдельное сравнение с фактом. `--compare` для SQLite читает целевой факт после сохранения прогноза. По умолчанию используется `rr1plus_data_raw`; SQLite открывается только для чтения. При запросе будущего плана выбираются ключи, `target` и дата доступности, а не будущие поля факта/долга.

`--config config.json` позволяет задать все поля `Config`, включая отдельную таблицу плана, сегменты и дополнительные источники. Для Parquet установите также `pyarrow`. Даты по умолчанию ISO; числовые даты задаются через `raw_date_encoding`: `yyyymmdd`, `s`, `ms`, `us`, `ns`. Даты без часового пояса считаются московскими; даты с поясом переводятся в Москву.

## Проверка на истории

По умолчанию: 6 месяцев для выбора модели, затем 3 месяца для независимой проверки перед целевым месяцем; каждому прогнозу предшествует минимум 12 полных обучающих месяцев. Требуется как минимум 21 полный исторический месяц. Например, для ноября 2026 разработка — февраль–июль 2026, контроль — август–октябрь 2026.

Границы меняются через `development_start`, `development_end`, `control_start`, `control_end`, `min_train_months`. Все они должны идти последовательно и предшествовать целевому месяцу. Для каждого месяца прогноз выпускается из конца предыдущего; внутримесячного обновления нет. При задержке закрытия факта используйте реальную дату доступности через `raw_available_column`.

Модель и веса выбираются по максимальной ошибке в п.п. на разработческих месяцах, затем по средней ошибке. Это показатели подбора, а не независимый результат. Контрольные месяцы оценивают уже зафиксированную конфигурацию. Повторное обучение на доступной к очередному прогнозу истории разрешено; выбор модели по контролю не производится. Все кандидаты соревнуются на одинаковых полных месяцах. По умолчанию некомплектный месяц останавливает расчёт, а не исчезает из оценки незаметно.

Версии плана и фактов отбираются на дату выпуска. Без `plan_available_column` и `raw_available_column` невозможно восстановить поздние пересмотры: аудит явно отмечает этот режим, а пользователь должен предоставить исторически доступные данные. Летне-осенняя проверка не доказывает точность в январе и декабре.

## Реализованные модели

- Нормированный референс: накопленная кривая переносится по доле прошедшего месяца, сохраняя конечное выполнение при 28/29/30/31 днях.
- Календарный профиль: историческое отношение сбора к плану по календарным группам.
- Регуляризованная календарная регрессия для общего ряда, включая подписанные корректировки.
- Общий CatBoost по сегментам с двумя целями: дневной и накопленный сбор; независимый общий CatBoost для выполнения плана.
- SARIMAX общего дневного ряда с известным планом, календарными регрессорами и недельной сезонностью.
- Согласование сегментных прогнозов с общим прогнозом; веса выбираются на разработческих месяцах, денежные поправки сохраняются.

Признаки включают будущий календарь и утверждённый план, последний доступный портфель, доли долга, историческое выполнение и сборы за предшествующие 7/14/28 дней. Никакие лаги не читают факты целевого месяца. Календарь РФ строится через `holidays`, включая переносы; утверждённый календарь можно передать через `calendar_path`.

Дополнительные CSV/Parquet-источники задаются через `portfolio_path`, `inflow_path`, `operations_path`, `reference_path`. Заголовки приведены в `input/*_template.csv`. Обязательны временные метки `known_at`; данные соединяются на уникальной детализации сегмента. Коммуникации более крупной детализации сначала нужно корректно агрегировать/нормировать, а не размножать их количества по детальным сегментам. Отсутствующая операционная история сохраняется как неизвестная.

В этой версии публикуются точечные прогнозы. Статистически откалиброванные интервалы требуют отдельного периода калибровки и проверки покрытия; допуск ±1 п.п. на графике сравнения является бизнес-критерием, а не доверительным интервалом.

## Результаты

В `output_dir` сохраняются:

- `forecast.csv`, `forecast_total.csv`, `forecast.html` — фиксированный прогноз по сегментам и в целом, выполнение плана и график даже без будущего факта.
- `development_ranking.csv`, `development_scores.csv`, `control_scores.csv` и дневные кривые — подбор и независимая проверка.
- `audit.json`, `manifest.json`, `model_status.csv`, `fold_log.csv` — режимы входов, доступность данных, конфигурация, контрольные суммы и исключённые модели/месяцы.
- При наличии факта: `comparison_total.csv`, `comparison_segments.csv`, `metrics.json`, `comparison.html`, `comparison.png`, `report.md`, разрезы по продуктам/DPD/PVR и календарным группам.

Частичный факт, пропущенный сегмент или неполная прогнозная сетка не могут получить статус достижения цели. Факт вне исходной плановой сетки учитывается в общей сумме и делает оценку неполной. Данные и отчёты исключены из Git; в БД код ничего не записывает.

Другой прогноз не может перезаписать уже сохранённый `forecast.csv`: для новой конфигурации/месяца выберите отдельный `output_dir`. Повторное сохранение идентичного прогноза разрешено. Фактические сравнения можно обновлять по мере закрытия месяца.
